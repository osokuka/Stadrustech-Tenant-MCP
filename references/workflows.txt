Hosted Tenant MCP — workflow string references (§17.3.2)
Source of truth for agents + FastMCP tool docstrings. Keep in sync with
workingscope/AI_FASTMCP_TOOLS.md and Stadrustech-Tenant-MCP docs/TOOLS.md.

--- tickets (tenant staff for any client) ---
Open: tickets_create · Assign: tickets_assign · Resolve: tickets_resolve ·
Status: tickets_set_status · Billing preview: tickets_billing / clients_retainer_hours ·
Priority: tickets_update(priority=…) · Comment: tickets_add_comment ·
List/detail: tickets_list / tickets_get · Comments: tickets_list_comments.

--- tickets.list “opened” (colloquial) ---
User says “any opened tickets” / “open tickets” / “what’s in progress or open”:
→ tickets_list(status="opened") [= unresolved|active|openish]
→ returns open + in_progress + pending (excludes resolved and closed).
Exact single status still: status=open|in_progress|pending|resolved|closed.
Optional client= after clients_resolve.

--- tickets.create ---
Gather: title (required), description (preferred), client UUID from clients_resolve
(preferred for SLA), priority (default medium), category (default incident),
optional location UUID, optional external_reference, service_rate_id from
clients_service_prices(client_id) (seeds billable_unit_price; optional
billable_unit_price override). Requires can_create_tickets. Status starts open; source=api.

--- tickets.billing / tickets.resolve (SLA + retainer) ---
Invoice lines are NEVER created by Tenant MCP. The backend adds/updates the draft
invoice line automatically when the ticket becomes resolved/closed
(sync_ticket_to_open_bill). Same for projects: projects_complete → draft proforma.
MCP only logs hours + billable flags + status.

Before finishing work on a client ticket:
1) clients_resolve → clients_retainer_hours(client_id) and/or tickets_billing(ticket_id, hours=…)
2) Confirm hours with the user.
3) tickets_resolve(ticket_id, hours=…, service_rate_id=?, billable_note=?, also_close=?)
   - hours retainer + pool remaining → is_billable=true (system €0 covered line on resolve)
   - pool exhausted → is_billable=true (system overage line on resolve)
   - mark_non_billable=true → goodwill (hours logged; system does not invoice)
4) billable_note = short work/service name ONLY (or omit → service_rate / ticket title).
   NEVER “covered by retainer”, “non-billable”, or billing commentary in billable_note.
Do NOT call any invoice create/add-line tool for tickets. Read invoices_* only to verify.

--- tickets.set_status ---
status=open|in_progress|pending|resolved|closed.
pending REQUIRES comment (SLA pause). Prefer tickets_resolve when finishing billable work.
Optional billing fields on resolve/close: billable_hours, is_billable, billable_note,
service_rate_id. is_internal_note hides comment from client portal. Needs can_update_tickets.

--- tickets.priority ---
tickets_update(ticket_id, priority=low|medium|high|critical). Needs can_update_tickets.
May affect SLA targets — tickets_recalculate_sla if due dates look wrong.
Bulk: tickets_bulk(ticket_ids, priority=…) for many tickets.

--- tickets.comment ---
tickets_add_comment(ticket_id, content, is_internal_note=false).
is_internal_note=true → staff-only (hidden from client portal). Needs can_create_comments.
List with tickets_list_comments (needs can_read_comments).

--- tickets.assign ---
technician_id = Django user PK (= technicians[].user_id from
assignment_list_technicians). Sets status in_progress. Needs can_assign_tickets.
Do NOT pass TenantUser UUID.

--- assignment ---
assignment_recommend scores only; assignment_auto_assign assigns best match
(needs can_assign_tickets). Filter techs by role/location/city; include_workload=true
by default.

--- discovery ---
search(q, types=clients,projects,tickets,invoices) for mixed lookup.
clients_resolve(q) when the user names an organization.
clients_pack(client_id) — SUMMARY only (prices_included=false). Not for quotes.

--- client process questionnaires (site assessment / onboarding) ---
ITSM stores these on the client record (Processes tab) via clients_process_*.
NO markdown/document upload tool exists — map findings into questionnaire items.
site_assessment (3 pages) = site visit / initial IT assessment / pre-contract.
client_onboarding (7 pages) = post-win ONLY — never for site assessment docs.
Never auto-started. Every answer MUST go through clients_process_update.
Never claim “ITSM has no questionnaire save”. Overflow → notes.
1) clients_resolve → clients_processes_list
2) clients_process_start(definition_key=site_assessment) for site visits
   (client_onboarding only post-win) or continue latest active_run_id
3) clients_process_get(run_id, unanswered_only=true) → present open questions
4) clients_process_update(items=[{id, answer, notes?}]) — one or many; any order
5) Repeat 3–4 until unanswered_count=0 (or user pauses)
6) clients_process_complete (confirm) or clients_process_abandon
On 403 / missing tools: reconnect Tenant MCP or report the error — never fake a save.
Never invent answers. Never store live passwords or API keys in answer/notes.

--- non-principal org people (ClientOrgPerson — NOT portal users) ---
Per-client when needed (site assessment / onboard / assign devices).
NEVER mix with Principal Users (portal accounts). Needs assets module.
1) clients_resolve → people_template(client_id) FIRST
2) Confirm name (+ email/dept/title/location) with the user
3) people_create(client_id, full_name=…) for a simple record
   OR people_onboard(…, assets=[{asset_id, role}], services=[…]) to link
4) List/search: people_list(client_id, active=true, search=…)
5) Offboard: people_offboard(person_id) → checklist + unlink + deactivate
Same write flags as devices. Never store passwords. Reconnect MCP if tools missing.

--- credential vault stubs (assessment → empty placeholders) ---
When a server/device is identified as having credentials (e.g. Domain Admin, iLO):
1) Do NOT ask the user to paste passwords into chat for MCP storage.
2) clients_process_vault_stubs_create or clients_vault_stubs_create with labels only
   (title, kind, host, optional username hint) → secret_status=empty
3) Put returned vault ids/titles into the process answer as references.
4) Tell user a vault operator must populate secrets in web: Client → Vault.
MCP NEVER accepts password/secret/api_key fields (server rejects 400).
No reveal / populate-secret tools on MCP. Client MCP has no vault tools.

--- risk assessment & register (module grc) ---
Needs grc enabled + can_read_risks / can_write_risks.
Cadence: formal min once/year + event-driven on infra change or mitigation done.
Kinds: ad_hoc | site_assessment | client_onboarding | periodic_annual |
  periodic_custom | nis2 | cmmc | iso27001
1) Site / onboarding → clients_process_* then
   risk_assessments_start(client_org=…, process_run=run_id)
   (kind inferred from process if ad_hoc)
2) Formal annual / NIS2 / CMMC / ISO → kind=periodic_annual|nis2|cmmc|iso27001
   List overdue: risk_assessments_list(overdue=true)
3) Infra change or mitigation complete → kind=ad_hoc (name the trigger in title);
   re-score affected risks; does not extend next_due_at
4) Interview → propose risks → confirm → risks_create
   (assessment=, roadmap=[…], delivery_vehicle=ticket|project|none — be decisive)
5) risks_set_treatment / risks_roadmap_set as needed
6) If mitigate: risks_create_ticket OR risks_create_project (confirm; links for UI)
7) risk_assessments_complete → next_due_at only for recurring/framework kinds
8) Exec view: risks_summary / reports_run(risks.heatmap); CSV via risks_export
Never paste secrets into evidence. Full NIS2/CMMC control libraries = later GRC.

--- GRC MVP + compliance spine (frameworks / enclave / SSP) ---
Needs can_read_grc / can_write_grc + module grc. Canonical: GRC_MODULE.md §2.2.
1) clients_resolve → grc_obligation_create/activate (required controls; L1 FCI then graduate L2)
2) grc_enclave_upsert (one enclave; kind fci→mixed/cui on same boundary)
3) devices/assets inventory → confirm → grc_enclave_members_bulk_set (side=in AND side=out)
4) grc_enclave_undeclared → keep shrinking; affirmation-ready blocks on undeclared
5) grc_assignment_create/update (active vs watch — watch packs do not drive readiness %)
6) grc_gaps / compliance-themes → grc_implementation_update (status, notes, planned_*)
7) Cover gaps: tickets_create / projects_create / risks_create_ticket|project
   WITH compliance_controls[] + enclave + contribution_kind (or compliance_contribution_create)
8) grc_compliance_kpi / grc_ssp_* — measurable contribution to SSP and framework readiness
Confirm before writes; no secrets in evidence notes. Billing stays on tickets/projects.

--- service offers / exact prices ---
PRIMARY: clients_service_prices(client_id) — exact client EUR/h (`rate`) + id/code/name + TSV.
Alias: clients_offer_prices (same payload) — use when the user asks for offer pricing.
clients_service_catalog(client_id) — same priced lines (default limit=80; page via offset).
clients_services = alias of clients_service_catalog.
services_list(client=…) priced; services_list() with no client = summaries only.
services_get(id) for one line (+ clients using that SLA).
Never invent rates; quote `rate` for that TenantClient only.

--- retainers / recurring (tenant staff) ---
Do NOT use projects_create for monthly retainers or recurring payments.
1) clients_resolve → clients_service_prices(client_id)
2) Draft a document in the AI chat (scope, included hours, monthly amount)
3) Tell user to create the recurring charge in web: Finance & Accounting → Finance → Recurring charges (pick client)
Clients may still create draft projects via Client MCP — that is fine.

--- projects (one-time / delivery only) ---
1) clients_resolve → clients_service_prices(client_id) [page if has_more]
2) projects_create(name, client=…, activities=[{service_rate_id, name?, estimated_hours?}…])
   REQUIRED ≥1 activity in create. description = short objective only (1–3 sentences).
   NEVER put work breakdown / numbered checklists / "is complete when" in description —
   those are activity rows. Do not invent default_hourly_rate; avoid billing_model=retainer.
3) optional project_activities_create for extras; materials → projects_set_offer_validity →
   projects_offer_pdf|html|xlsx
Approve client-submitted: projects_approve(project_id) when status=submitted → planned.
Projects module must be enabled or tools return 403.
billing_model for delivery: time_and_materials|fixed_price.

--- activities / materials ---
project_activities_create REQUIRED: project UUID + service_rate_id from
clients_service_prices (catalog seeds name, default_hours, hourly_rate).
Optional name / estimated_hours / hourly_rate (staff override) / dates YYYY-MM-DD.
status planned→…→done. Materials: name, quantity, unit, unit_cost (staff can set costs).

--- invoices ---
Needs can_read_invoices. Filter by client UUID/name, billing_cycle, status,
billing_kind, settlement, search. invoices_pdf returns base64 PDF.
Send / resend: invoices_send_email(invoice_id, optional to/cc/note) — confirm first.
  First send sets email_sent_at; same tool resends.
Reminders (per invoice, after first send only):
  invoices_set_reminders(invoice_id, enabled=true|false, interval_days=15)
  Unlock fails until Email/Send. Interval 1–365 days (default 15).

--- reports ---
reports_list → reports_schema(report_id) → reports_run(report_id, period|from/to,
optional client_id). clients.overview / tickets.hours are tenant-staff only.

Weekly hours + billable split (agent report):
  Prefer from_date/to_date when the pack week is custom (e.g. Friday Berlin cutover):
    reports_tickets_hours(client_id=…, from_date=YYYY-MM-DD, to_date=YYYY-MM-DD)
  Or period=week only if Monday→today is acceptable:
    reports_tickets_hours(period=week, client_id=…)
    reports_run(report_id=tickets.hours, period=week, client_id=…)
  → totals.hours_logged / hours_billable / hours_non_billable
  → rows[].billing_status (billable|non_billable|hours_not_logged)
  → clients[].hours_remaining + retainer_hours (current month pool)
Single ticket fallback: tickets_get → hours_logged, billing_status, billing.retainer_hours.
